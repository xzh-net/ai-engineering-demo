## 1. 核心信息（读者必须一眼看懂的三条）

1. **多个业务应用（管理后台 / 门户端 / 小程序）共用一个统一消息中心和一套订阅授权页**，不是各建一个推送系统。
2. **订阅授权与触达准入是两个独立环节** —— 关卡 A（订阅授权）通过 ≠ 一定能收到消息；
   关卡 B（触达准入）可以单独拒绝，且**拒绝时不得丢失订阅关系**。
3. **换账号不串数据**：用户切换账号后，原账号的订阅关系不得被新账号继承；应用须对新账号重新发起授权。

## 2. 业务需求

### 2.1 参与角色与基础设施

| 角色/设施 | 职责说明 | 图上颜色 |
|---|---|---|
| 终端用户 | 订阅关系的拥有者，可授权、拒绝、退订 | 蓝 `#dae8fc` |
| 业务应用（三端） | 管理后台、门户端、小程序发起订阅与接收推送结果 | 绿 `#d5e8d4` |
| 统一消息中心 | 订阅授权处理 + 触达准入判断（两关卡所在） | 紫 `#e1d5e7`（描边 `#7b4bb5` 3px） |
| 订阅关系与规则数据库 | 订阅关系、账号归属、类目配额、免打扰与黑名单规则 | 灰白圆柱 |
| Redis | 待发送队列状态、限流计数、去重窗口 | 灰白圆柱 |
| 消息推送通道（外部） | 实际投递到终端；属外部依赖，画为灰色节点 | 灰 `#eeeeee` |

### 2.2 关卡 A · 订阅授权（紫色）

- 业务应用在用户操作后发起订阅请求（如点击「订阅发货通知」）
- 未登录 → 先走应用自身的登录；已登录 → 直接进入授权环节
- 拉起**统一订阅授权页**，展示将要订阅的消息类目与频率
- 用户**确认授权** → 消息中心写入订阅关系（账号 + 应用 + 类目 + 有效期）
- 用户**拒绝** → 不写入订阅关系，应用按降级策略处理（如仅站内展示）
- 授权完成 → 向业务应用返回**授权结果**（成功 / 拒绝 / 已存在）

> 图上标记为「关卡 A · 订阅授权」。**授权只代表用户同意，不代表消息一定能送达。**

### 2.3 关卡 B · 触达准入（橙色容器 + 红色判断菱形）

- 取得：**待发送消息 + 目标订阅关系 + 来源应用**
- 查询：**类目配额、免打扰时段、用户黑名单、订阅有效期**
- 判断：**该条消息是否允许在此刻发给该用户**
- 允许 → 进入推送通道投递（绿线）
- 不允许 → 按拒绝原因分流：
  - **免打扰 / 用户退订** → 本次不发，**订阅关系按规则保留或终止**
  - **类目配额用尽** → 转入延迟队列，次日配额重置后重试
  - **订阅已过期** → 不发，提示应用引导用户重新授权
- 判定结论必须回写，供应用查询**投递结果**

> **铁律**：拿到订阅授权不等于能发；触达准入是**独立于授权**的第二次检查。
> **关卡 A 与关卡 B 必须是两个独立的 mxCell 容器。**

### 2.4 业务路径

| # | 路径 | 图上表现 |
|---|---|---|
| 1 | **正常**：应用发起订阅 → 授权页确认 → 写入订阅关系 → 后续触达准入通过 → 投递成功 | 主链，黑实线 |
| 2 | **用户拒绝授权**（关卡 A 拒）：授权页点「不允许」→ 返回应用 → 应用降级为站内展示 → 不产生订阅关系 | 红虚线回退支路 |
| 3 | **已授权但触达被拒**（关卡 B 拒）：配额/免打扰 → 本次不发 → 延迟重试或转站内信 → **订阅关系保留**，下次仍可发 | 红虚线进橙色区 + 绿色延迟分支 |
| 4 | **重点：换账号不串订阅**：用户以账号甲授权 → 退出并改用账号乙 → 应用以账号乙重新发起订阅（关卡 A 重新走）→ 甲的订阅**不得出现在乙名下** | 橙色区 + 黄色便签说明 |

### 2.5 专项流程：消息配额延迟重试

1. 触达准入判定为「类目配额用尽」
2. 消息写入延迟队列，标记 `待重试`
3. 次日配额窗口重置 → 重新进入关卡 B 判定
4. 连续 3 次仍被拒 → 终止并通知应用，**订阅关系保留**

> 延迟重试属于**触达准入的延伸**，与订阅授权无关；是否拆成独立图见 §6。

### 2.6 表达禁则（本业务特有）

> 通用禁令（接口路径、类目编码、框架名、队列组件、Token、限流算法实现）默认适用，此处不重复。

- ❌ 把「订阅授权」和「触达准入」画成同一个判断框
- ❌ 把三个业务应用画成三套独立的推送系统
- ❌ 隐去「授权成功但触达被拒」这条路径（这是两关卡分离的证明）
- ❌ 画入具体推送通道商名称、MQ/队列选型、重试代码逻辑

## 4. 设计决策记录

| # | 决策 | 原因 |
|---|---|---|
| D1 | 沿用**关卡主视图**布局（左三端 → 中央双关卡纵向 → 右侧数据与结果 → 底部专项流程） | 与第一张图（统一认证中心业务流程图）保持同一视觉语言，便于横向对比；实践证明比泳道布局直观 |
| D2 | 关卡 A/B 左右并排、流程 A→B→A 只做一次短横跳 | 一眼看出两道独立关卡，避免纵向折返 |
| D3 | 触达拒绝用**橙色区**而非红色；「延迟重试」用**绿色**表示最终仍会送达 | 与认证图的"红色=永久拒绝"区分语义——触达拒绝多数是**可恢复**的 |
| D4 | 推送通道画为灰色外部节点，不画具体通道商 | 属外部依赖与选型细节，非业务规则 |
| D5 | 图的坐标与文案只维护在 `gen-*.py`，本说明书不复制坐标表 | 避免两份坐标不同步 |
