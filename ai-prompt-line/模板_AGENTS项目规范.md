# 模板：AGENTS 项目规范（新项目直接复制改造）

> 用法：① 手动——复制本文件为根目录 `AGENTS.md`，按标注逐项替换；② 推荐——作为 P1 提示词的**输入槽**，由 AI 按方案生成。
> 标注体系：**【必改】**= 不改会让机制失灵｜**【按需】**= 有对应场景才留｜**【结构必留】**= 正文可微调但环节不能删
> 主文档：`2026-10-31_AI编程指南_新项目快速生成AGENTS与状态机.md`（快速通道 + 生成过程 + 提示词）
> 配套：`模板_验证阶段工作流.md`（P2 分册生成来源）、`模板_技术选型方案.md`（P0 结构契约）

## 前置条件（开写之前你要准备的）

1. 明确**功能目标、目标平台、语言、核心能力清单**（3–6 项），写成需求文档（可按 `模板_需求.md` 结构）
2. 已拍板的**技术选型方案**（由手册 §五 前置的 P0 生成并经你确认）
3. 项目目录已 `git init`（手册 §五 Step①；`.gitignore` 与 `docs/` 目录由 P2 统一生成）
4. 后续所有 AI 会话**以项目根为工作目录**（AGENTS 自动加载的前提）

## 二、项目文档管理规范

### 2.1 文档优先原则

开始任何开发任务前，按序读取：1) 方案基线文档 → 2) 架构文档 → 3) 需求文档 → 4) 近期开发记录 → 5) 验证/问题/决策记录 → 6) **当前激活的阶段分册**（见 §1.2）。
文档与代码不一致时：不先认定文档错 → 查最近记录与决策 → 分析差异 → 必要时问用户 → 确认后同步文档。

### 2.2 文档分类与根目录规则【必改：按项目裁剪】

| 文档类型 | 保存目录 |
|---|---|
| 需求文档 | docs/需求文档/ |
| 技术选型 | docs/技术选型/ |
| 架构设计 | docs/架构设计/ |
| 开发记录 | docs/开发记录/ |
| 验证记录 | docs/验证记录/ |
| 问题记录 | docs/问题记录/ |
| 技术决策 | docs/技术决策/ |
| 阶段工作流分册 | docs/工作流/ |

**项目根目录只保留**：`docs/`、`AGENTS.md`、`README.md`（`.git/`、`.gitignore` 除外）。代码与运行数据统一在 `{code}/` 下。
> 简写约定：下文 `src/`、`poc/` 等均指 `{code}/` 下对应目录。
> 包名：发行名 `{kebab-name}`，导入名 `{snake_name}`，源码位于 `{code}/src/{snake_name}/`。

### 2.3 文档命名【结构必留】

`YYYY-MM-DD_文档名称.md`，日期用实际创建日期，不允许伪造。

### 2.4 验证结论回写规则【结构必留 · 最重要的一条文档规则】

每个验证阶段结束后必须**双写**：
1. 完整过程 → `docs/验证记录/`（含预期/实际/环境/步骤/成败/原因/后续）
2. 结论 → 方案 §X 验证路线对应阶段处，追加"验证结论 · 阶段N"小节：**通过/不通过 + 实测数据**；不通过则启用预案，新决策另建技术决策记录
方案中"待验证"标记验证后必须更新，不留悬空。

## 三、持续开发工作流程【结构必留】

所有任务先分类、再执行（激活分册见 §1.2）：

| 任务类型 | 特征 | 执行方式 |
|---|---|---|
| 验证任务 | 回答方案某验证项的"通过/不通过"，产出数据 | 按激活分册的验证特化六步 |
| 工程/开发任务 | 工程初始化、配置、日志、文档等稳定部分 | 按下列通用六步，受 §1.5 门禁约束 |

通用六步：
1. **理解任务**：读需求、看结构、读相关文档与近期记录，明确涉及文件——不了解现有代码不许直接重写。
2. **分析与规划**：改代码前说明现状/目标/改动面/思路/**验证方式（环境+判定标准）**/风险；简单任务可直接执行；架构、核心依赖、库表、选型变更必须先获确认。
3. **实施**：优先复用、小范围修改、避免无关重构、不为小功能引大依赖、无循环依赖、异常可捕获可记录、留类型注解与注释、不硬编码掩盖配置问题；一次任务只解决一个问题。
4. **功能验证**：语法/导入/单元/模块/集成/运行结果，按改动相匹配；真实设备能力必须区分四级状态（代码完成/模拟环境/真机/未验证），**不能把写完说成验证通过**；无法测试必须明说。
5. **开发总结**：更新对应记录；改变选型或架构的，记录决策并按 §2.4 回写方案。
6. **向用户汇报**：按 §十格式，不虚报、不省略异常。

## 十一、最高优先级原则

1. 用户明确提出的需求优先于 AI 推测。
2. 已确认的技术选型（方案文档）优先于 AI 自行推荐；已否决方案不得擅自翻案。
3. 已有代码和项目历史优先于重新设计。
4. 实际验证结果优先于理论推测。
5. 未经验证的功能不能声称完成。
6. 重要技术变更必须记录并回写方案。
7. 不能为了完成任务而掩盖错误。
8. 不为一次性完成做无关的大规模修改。
9. 每次迭代保持**代码、文档、实际验证结果三者一致**。

**核心开发理念：小步开发、逐步验证、持续记录、稳定迭代。**
