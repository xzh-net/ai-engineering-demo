## §一 AGENTS 是什么

**一句话定义**：放在项目根、被 AI 会话**自动加载**的规范文件——它是 AI 的**长期记忆替身 + 行为契约 + 项目状态看板**。

**决定后面一切机制的三个物理事实**：

1. 它是**静态文本**，永远不会自我修改；
2. 只要会话的**工作目录 = 项目根**，它就全文注入 AI 上下文（唯一硬前提）；
3. **AI 没有跨会话记忆**——今天没写进 AGENTS 的事，下个会话等于从未发生。

**它不是什么**：

- 不是 README（给人看的只是一句话定位）；
- 不是文档仓库（过程细节放 `docs/`，AGENTS 只放规则和指针）；
- 不是自动的（"更新"只能是任务里的显式动作，靠规则强制，见 §二五件套）。

**它解决什么**：① 换会话不丢上下文；② AI 行为不随聊天漂移；③ 项目状态永远有唯一真源。

### 2.3 两个常见疑问的标准答案

**问：新会话怎么"感知到"之前的进展？**
答：三步，全是读文件——① 工作目录对 → AGENTS 自动加载；② 看 §1.2 知道**什么阶段、按哪套分册干活**；③ 看 §1.6 知道**进行中/挂起/下一步**。细节（当时的数据、日志）去 `docs/验证记录/` 等目录读。示例见 §4.1。

**问：AGENTS 会自己更新吗？**
答：**不会**。没有系统级自动机制。你看到的"更新" = 必报项强制某个会话的 AI 在收尾汇报时**显式改文件**。"自动"是（自动加载 × 必报强制 × 任务闭环）每圈都转出来的**涌现效果**，动手的永远是"那个会话的 AI 按规则干的"。

### 2.4 人机分工（一句话 + 三张清单）

**AI 管干活和保鲜，你管拍板和纠偏；文件永远不用你动手，方向永远不交给 AI 自作主张。**

| 谁 | 干什么 |
|---|---|
| AI 自走 | 每任务状态更新、双写、续接、执行切换清单的机械步骤、主动提示规范缺口（**提议不擅改**） |
| 必须你拍板 | 不通过预案二选一、挂起事项（参考项目 §1.6 挂起队列）、架构/核心依赖/选型变更、需求与合规、git commit/删除 |
| 你盯最后一道防线 | 三个失效信号：汇报长期"无需同步"／§1.6 落后一个任务／方案"待验证"悬空超一个阶段——出现即让 AI 补 |

## §四 使用指导

### 4.1 解决"后续会话自我感知"——AGENTS 里应该怎样写（举例）

原理一句话：AI 的"感知上个会话"= **读文件**，所以必须把"接头暗号"写在**固定位置**，让每个新会话一进来就知道去哪看。

**三个必写点 + 参考项目真实原文：**

**例 A —— §1.2 头部指针行（状态机开门第一行）**

> 原文（`AGENTS.md` L28）：`**当前阶段：验证阶段** ｜ 激活分册：docs/工作流/验证阶段工作流.md`

作用：新会话读一行就拿到"现在在哪 + 按哪套手册干活"两个关键信息。
反例：只写"项目介绍"不写这行 → AI 知道项目是什么，但不知道干到哪，只能追问你。

**例 B —— §1.6 头部的"续接三步"（写给 AI 自己看的操作说明）**

> 原文（`AGENTS.md` L107）：`新会话续接三步：① 以项目根 D:\xuzhihao\emu-pilot 为工作目录新建会话，本文件自动加载…；② 看 §1.2 确认阶段与激活分册；③ 看本节"进行中 / 挂起 / 下一步"直接继续。细节去处：docs/验证记录/…`

作用：把"怎么续接"本身写进文件——AI 不需要被教，读完就会做。
要点：**连"工作目录必须是项目根"都写进去**（这是唯一硬前提，别指望人记得）。

**例 C —— §十"状态同步"必报段（让感知材料永远新鲜）**

> 原文（`AGENTS.md` L674）：`状态同步：说明本次是否需要更新阶段状态（四项）：AGENTS §1.2 阶段看板、§1.3 技术栈状态列、§1.6 进展快照、《技术选型方案》§六。…同时核对 §1.2「判定条件」：全部满足则当场宣告并按序执行「切换动作清单」；未全部满足则写明尚缺哪几条。`

作用：没有这段，例 A/B 读到的三天后就是过期数据。**自我感知 = 读得见（A/B）+ 保鲜得了（C）**。

**验收方法（拿新会话实测）**：开一个全新会话只问一句——"这个项目现在到哪一步、下一步干什么、按哪个流程？"答对 = 机制成立；答"我不知道/请补充" = 三个必写点缺了哪个，回 §3.2 补。

### 4.2 解决"方案从验证 → 落地 → 指导正式开发"——验证状态机

**问题链**：设计方案写出来只是**假设** → 必须逐个技术点**真机论证**（带量化标准）→ 论证要**可控推进**（不带病进下一阶段）→ 全部论证完要**平滑切换到正式开发**。这条链需要一个"进度条 + 道岔"——这就是**验证状态机**。

**先纠正形态认知**：状态机**不是独立文件**，它是 AGENTS **§1.2 章节**；它是**索引式**的——只装四样东西（状态表 / 判定条件 / 切换清单 / 分册指针），**不装内容**（内容在方案、记录、分册里，靠指针引用）。

**如何使用（四步循环，每个阶段转一圈）**：

```
① 开工：读 §1.2 → 当前阶段 + 激活分册（由 §1.2 指针给出；参考项目在 L28）
② 执行：按分册"验证六步"做真机验证 → 拿量化数据（不达标先归因再启用预案）
③ 收尾：必报回写 → §1.2 打勾/§1.3 状态列/§1.6 快照 + 验证记录存档 + 方案 §X 结论回写
④ 关口：核对判定条件 → 未满足：进下一验证项；全满足：当场执行切换清单
        （1 建开发分册改指针 2 归档验证分册 3 状态表改"正式开发阶段" 4 回写方案/决策）
```

**模板**（§1.2 最小骨架见 §3.2 ①；分册模板见 `模板_验证阶段工作流.md`——近零改动可复用）。

**切换后 AGENTS 什么形态**（提前知道终点）：

- **脚手架烧尽**：门禁按自毁条款失效、判定条件/切换清单一次性执行成历史、验证回写规则触发改为"新选型才回"——约瘦 1/4–1/3；
- **契约永驻**：§1.6 快照、必报项、代码/汇报/优先级、**否决清单**（确定后更要防 AI"好心优化"翻案）原样保留；
- **机制可重挂载**：将来换选型，把 §1.3 状态列改回"待验证"，门禁与验证分册重新生效——它休眠，不销毁。

**参考项目外联**：状态机本体 = `AGENTS.md` L26–57；激活分册 = `docs/工作流/验证阶段工作流.md`（L3 反向回指"所属 §1.2"）；回写实例 = 方案 L229/L240（阶段 0/1 结论）。

## §五 新项目三步走

**前置（不在三步内）**：一段功能目标（零散想法也行）→ **【R】** 产出需求文档（按 `模板_需求.md`，含事实提案清单等你确认）→ **【P0】** 出技术方案（含候选对比、否决留痕、带量化标准的分阶段验证路线）→ **你拍板定基线**。

| 步 | 动作 | 用什么 | 检验标准 |
|---|---|---|---|
| **① 落模板** | 新项目根放 `AGENTS.md`（复制 `模板_AGENTS项目规范.md`）+ `git init`（`docs/` 目录、分册、`.gitignore` 全部由 P2 统一生成——同一产物只留唯一责任人） | `模板_AGENTS项目规范.md`（附录含速查表） | AGENTS 模板就位、git 仓库就绪 |
| **② 生成真实文件** | 在**项目根开新会话**，发 **【P1】**（模板+方案 → 真实 AGENTS+状态机，AI 自查必改清单并列假设等你确认）；接 **【P2】** 建目录/分册/查 git status | §5.2 提示词 | 无 `{占位符}` 残留；§1.2 判定条件与你方案的阶段一一对应；**分册含按阶段分组的验证项清单，逐项能对回方案行** |
| **③ 首任务闭环** | `git commit` 首提交 → 发 **【P3】** 跑第一个验证任务 → 收尾八段必带状态同步 | 【P3】 | 文件里能查到该任务落盘的状态更新（用 §4.1 验收法实测续接） |

### 5.2 提示词原文（复制即用，替换 {花括号}）

**【R】把想法整理成需求文档（任意会话，可与 P0 同会话续）**

```text
当前工作目录就是新项目根。输入：
- 需求模板：{模板_需求.md 的内容}
- 我的想法：{零散想法/背景/一句话目标——越乱越好，就是要你来整理/例如：基于 Java 和 SQLite 开发一个一体化（单体）图书馆管理系统，涵盖图书管理、读者管理及借还书等核心功能}
按模板结构产出**本项目真实需求文档**（1 目标【含能力表】/ 2 边界与性质 / 3 其它约束 / 4 提案与假设清单）：
1. 能力表：从我的想法提炼 3–6 项，**一行一能力、可验收**；你觉得缺了的补上并在提案清单标注；
2. 燃料事实必须显式化：影响后续验证阈值的具体数字与事实——目标规模（几实例/几类页面）、
   目标机器配置、运行时长/频率约束——写不出的标【需求待确认】；
   （需求里每多一个事实，下一步方案里就少一条【阈值待拍板】）
3. 提案纪律（禁止开放式提问）：只有我能定的事实（规模、机器、使用者、授权范围、不做的边界），
   写入模板第 4 节《提案与假设清单》：逐项给出建议默认值 + 理由 +【需求待确认】标记，等我确认；
   常识可推导的直接填默认并列入假设清单，不提问；
4. 只写"要什么"，不写"用什么技术"（技术选型是下一步 P0 的事）。
保存为 docs/需求文档/{YYYY-MM-DD}_{项目名}需求.md；生成后自查：四节齐（第 1 节含能力表）？能力表可验收？
事实类缺口是否全部进提案清单？——逐项报告，等我确认后再定稿。
```

## §六 常用指导（活章节——新问题解决后往这里补）

**补充格式**（每条三行，规则一句话，机理指回正文）：

```markdown
### N. 问题一句话
- 现象：
- 判断方法：
- 处置：（一句话规则；能落成 AGENTS 条文的就注明落哪条）
```

### 1. AI 声称"已更新/已验证"，但文件里查无此状态

- 现象：会话汇报说某状态已更新，翻文件却没找到（或反过来，把"必报项的更新区域清单"误读成了"已更新的结果"）。
- 判断方法：**证据链核对**——§1.2 看板 ↔ §1.3 状态列 ↔ §1.6 快照 ↔ 方案 §X 回写，外加 `docs/验证记录/` 有无当次档案；状态一律**以文件实际内容为准**。
- 处置：让 AI 补落盘（虚报则按 §8.1 记问题）；长期如此说明必报项执行在漏，回到 §2.2 件套 5 检查汇报格式。（机理见 §2.3 问答 2）

### 2. AI 未经明确告知就抢跑执行任务

- 现象：你只说"考虑/准备"，AI 已经动手改文件、跑命令。
- 判断方法：任务性质是否到了"明确指令"级。
- 处置：当场叫停 + "**把这条写进 AGENTS**"（落成 §三流程约束："先答复、得到明确告知再开始"）。（本项目实录：A 任务半程被叫停后入规）

### 3. 新会话答不出"项目到哪了"

- 现象：开新会话，AI 追问你项目背景。
- 判断方法：§4.1 验收法三问（到哪步/下一步/按哪个流程）。
- 处置：对照 §3.2 补齐三个必写点（§1.2 指针行、§1.6 续接三步、§十必报段），并确认工作目录=项目根。

### 4. 终端输出中文乱码，疑似文件损坏

- 现象：命令回显里路径/中文全是问号或方块。
- 判断方法：**用文件读取接口核对**（读文件工具/编辑器），不要信终端回显。
- 处置：多为控制台编码问题，文件完好则不动；仅当读接口也显示异常才修文件。（本项目实录：pyproject 曾被误判损坏，实为 GBK 显示问题）

### 5. 状态机内容无处落位 / 被写进了方案

- 现象：生成 AGENTS 后 §1.2 空洞，状态与阶段内容堆在技术选型文档里；或 AI 自行新建了一个"状态机文件"。
- 判断方法：**§1.2 四件套检查**（状态表 / 判定条件 / 切换清单 / 激活指针）+ 判定条件与方案行项 1:1 + 方案内无 ✅/⬜ 看板。
- 处置：按 §5.1 映射表回炉 P1 第 2 条（模板 §1.2 骨架 → 落 AGENTS §1.2 → 内容取方案 → 禁入方案）。（实录：2026-11-01 实测发现旧版 P1 未写输出路径与模板映射，AI 只能自由发挥）

### 6. 生成的分册是通用骨架，验证标准看似要自己写

- 现象：P2 跑完打开分册，只有通用六步，没有本项目的验证项/标准/预案，误以为标准要手工填。
- 判断方法：分册有无"**本阶段验证项清单**"章节，且逐项能对回方案 §X 行。
- 处置：重跑增强版 P2（读方案阶段表 → 生成清单章节，标准值带出处）。（实录：2026-11-01 实测发现旧版 P2 只替换方案名，缺"方案 → 分册"内容实例化）

### 7. P0 产出缺"架构/自研边界"，P1 无依据可依

- 现象：P0 方案有候选对比和验证路线，但没有整体架构分层/模块划分，也没写自研聚焦——P1 生成 AGENTS §6.1 模块表与 §5.1 时无据可编，只能瞎编或抄模板。
- 判断方法：对照 `模板_技术选型方案.md` **九节契约**逐节打勾，重点看第 3 节（架构与模块）与第 2 节（自研聚焦）。
- 处置：按模板重跑 P0，或手补该两节后再发 P1。（实录：2026-11-01 测试项目 P0 第一版缺此两节）

### 8. 提示词引用模板却未指名文件 / 无输入槽

- 现象：提示词说"把模板 X 实例化"但没写哪个文件、也没输入槽——提示词被单独复制使用时 AI 看不到模板，只能自编结构或反问。
- 判断方法：逐条检查提示词——凡引用模板处，是否自含"**文件名 + 输入槽（内容/路径）**"。
- 处置：补输入槽（如 `- 分册模板：{模板_验证阶段工作流.md 的内容}`）。（实录：2026-11-01 测试项目 P2 缺分册模板指名、P1 引用速查表无出处）

### 9. 同一产物被两个步骤同时管理（双责任人病）

- 现象：两个步骤/提示词都声称生成同一文件或同一产物（如分册、目录、.gitignore），结果互相覆盖、都不彻底，或使用者分不清归谁管。
- 判断方法：任一产物列出**唯一 owner**（哪一步生成、其它步骤只引用不重建）。
- 处置：收敛唯一责任人，另一处改为引用。（实录：本套件复发三次——分册落盘、docs 目录、.gitignore，均经实测暴露后收敛为"P2 统一生成"）

### 10. 只修了实例没修工具，缺陷跨项目复发

- 现象：某缺陷在 A 项目修好（只改了产出文件），换新项目同类缺陷原样再犯。
- 判断方法：**同一形态缺陷跨项目复现 = 规格缺口**，回查当时修的是实例还是工具侧（提示词/模板/QC）。
- 处置：修实例的同时**同步回灌工具侧条款**，两处一起落。（实录：2026-11-01 `§X` 占位——test20 只改了实例文件，test111 P1 三处复发，随后 P1 第 1 条补"全形态占位 + 实号解析"）

### 11. 质检判据误伤模板授权的合法内容

- 现象：QC 过检表把合法写法判违规（拍板表 ✅ 被"看板零出现"误杀）。
- 判断方法：判据与模板原文对照——模板明文允许的写法，判据不得禁止。
- 处置：收紧限定词（"阶段看板 ⬜🔄"而非泛指 ✅），并回查该判据此前的判定是否误伤。（实录：2026-11-01 QC 首次实战发现 §二第 8 条过宽——**标准自身也需要过检**）

### 12. P0 输入口写成开放式，核验信号误伤转正件

- 现象：P0 提示词输入槽含"可先按模板撰写"（读作输入可现写、可回问），卫生段以"〔燃料〕类教学标注"作样例信号——test111 合格转正件（图书馆需求）自带标注头与〔燃料〕标记（R 提示词自身要求产出），会被误判退回。
- 判断方法：拿真实转正件对照判据——凡 R 工序自身要求产生的标记不得作样例信号；样例的可靠判据 = 标题含"样例" + 免责头 + 落点不在 `docs/需求文档/`。
- 处置：输入槽改声明式（已转正+规范落点）并明写"封闭输入：只消费、不改写、不回问，缺口走 §9"；卫生段改核验门（判据→不通过即停→通过即生成），信号换为标题/免责头/落点三取一。（实录：2026-11-01 图书馆需求送检暴露，手册 §5.2 P0 前两行据此重写；机理见 §5.2 P0 输入槽与输入卫生）

### 13. 手册文件名与配套引用两套称谓并存（引用断链）

- 现象：全仓 5 处引用 `2026-10-31_AI编程指南_….md`，实际文件名却无日期前缀、且零处引用实际名——引用全部指向不存在的文件。
- 判断方法：QC §六 grep #5（配套列文件都存在）+ grep #1（旧文件名）：按引用名反查实体、按实体名反查引用，两向都跑。
- 处置：改名与改引用二选一收敛单一真源——按 AGENTS 文件地图与手册自标日期为权威，`git mv` 改回带日期名（1 处改动 vs 5 处引用），改后重跑 #1/#5。（实录：2026-11-01 P0 输入口修改的修后审计暴露，初始提交即断链；改名方案经拍板执行）

### 14. "改名"被执行成复制，孤儿旧件与计数/输入槽类缺陷一并复发
