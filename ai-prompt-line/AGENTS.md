## 一、项目定位

**ai-prompt-line** 是一条"从零散想法到 AI 可执行项目规范"的**提示词生产线**：四套模板定版式、R/P0–P2 四道工序压制成型、P3 进入任务循环；`标准_产物质检清单.md` 是各工序的质检标准。

本仓库性质：**纯文档 + 提示词仓库，无运行时代码**；首个方法论自举对象是它自己（本仓库自身的 `AGENTS.md` 手工维护、不经管线生成），第二个是参考项目 emu-pilot 的方法论来源。

**三个认知（新会话防错）**：

1. 本仓库**生产**别的项目的 AGENTS——但**自己的 AGENTS 例外**（手工维护）；**禁止**用 R/P0–P3 改写本仓库文件。
2. 双层结构：手册（对人，含提示词原文）/ 模板（对工具，结构契约）/ QC（质检，随产出物流动）——改内容先问"这属于哪一层"。
3. **手册 §六种子 = 本仓库的 changelog**——问题处理与经验回流的唯一入口。

## 三、修改纪律（问题处理方式 · 自我修复 playbook）

1. **分层修复**：病在提示词/模板/手册结构/QC 哪一层，只改那一层（病层定位表见 `标准_产物质检清单.md` §五）——跨层连改是事故之源。
2. **经确认执行**：任何文件改动先向用户说明（改哪、为什么、影响哪些引用），确认后动手；无自动回写。
3. **修改三步**：① 改一处 → ② **交叉引用审计**（跑 QC §六的六条 grep，零异常才算完）→ ③ 在手册 §六记种子（现象/判断/处置/实录）或更新条目。
4. **泛化三不**：不硬编码章节号（用 §X，不用 §六）、不硬编码实例名（用 {分册名}）、不给同一产物留第二责任人。
5. **规则住模板、提示词只管动作与纪律**：能沉进模板结构的规则不写进提示词（防两处漂移）。

## 四、送检与修复流程（产出物审计）

- 用户送检（产出物全文 + 工序名 + 所用模板）→ 会话按 `标准_产物质检清单.md` 对应工序**过检表**逐项核 → 输出三段式报告（过检 / 不过项+病层 / 修法建议）→ **根因在被检项目**按其 AGENTS 修；**根因在本仓库**按本文件 §三修 → 修后跑 QC §六审计 grep → 种子记录。
- 触发者永远是用户手动送检；**本仓库不设任何强制送检/必报机制**。

## 五、交付汇报（精简七段，去必报）

向用户汇报修改/审计时给出：本次任务 / 修改文件 / 实现内容 / 审计结果（含 grep 六条结论）/ 记录位置（种子条目号）/ 遗留问题 / 下一步建议。

**不设"状态同步"必报项**——本仓库无状态机，无状态可同步。

## 六、最高优先级

1. 用户明确指令与手动评审 > 本文件纪律 > AI 推测。
2. 不给本仓库引入自更新机制（状态机/门禁/必报/自动回写）——这是硬边界，任何会话不得以"完善机制"为由添加。
3. 与其它项目的关系：本文件**不由**本仓库模板生成，模板的适用对象是外部项目；两者结构相似是刻意为之（吃自己的狗粮），但生成关系不存在。
4. 未经验证的修改不声称完成；种子未记录不算收尾。
