## 一、定位与当前版本

**ai-prompt-line** 是一条从零散想法到"可验证技术选型"的提示词生产线。

- **主线目的**：需求 → 技术选型 → 验证执行 → 选型结论。
- **P1–P6 的角色**：当前执行验证、复盘与门禁的载体（AGENTS 状态机、验证分册、任务循环、验证报告、学习回路、门禁编排），也是验证通过后继续开发的载体；它们是手段，不是目的本身。
- **当前版本**：V1.0「可交付」——八段提示词（操作说明 S0–S9）+ 六份模板 + 质检清单 + 只读门禁检查器。V1.0 曾含黄金样例 `样例_完整项目/` 与 `--selftest` 回归基准，后按拍板移除（见 `修改记录.md`）；检查器回归改为对真实目标项目跑 `--root` 实测。

## 三、设计原理

### 1. 两层结构

- **规格层（Spec）**：模板、提示词、质检清单、九节契约——定义"什么算对"。
- **执行层（Runtime）**：状态、门禁、证据、学习、编排——保证"稳定做对"。

现状只有规格层，执行层从 V0.2 开始长。**规格层是执行层的规格说明书，不是它的替代品。**

### 2. AGENTS 的三个物理事实

1. 静态文本，永远不会自我修改；
2. 工作目录=项目根时全文注入；
3. AI 没有跨会话记忆。

所以：记忆必须写进文件；"自动"只能是"自动加载 × 必报强制 × 任务闭环"的涌现效果，不是系统级自动化。

### 3. 记忆与学习（V0.4 起机制化）

- **双记忆**：规则记忆 = 项目 `AGENTS.md`（跨会话注入的长期约束）；案例记忆 = `docs/学习记录/`（事实、证据、候选与去向）。
- **学习回路**：P5 复盘 → 案例记忆 → `L-NN` 规则候选 → 用户确认 → 项目环写入 AGENTS §1.8 → 下一任务/新会话/送检验证。
- **双环边界**：项目环可生效；工具环（跨项目模板/提示词/质检缺陷）只记候选，由用户人工回灌本仓——**本仓维持手工维护，不自动改写**。
- **门槛**：未确认不进规则，未验证不算学会。

### 4. 自洽不等于自觉

- 文档自洽：单一真源、引用不断链（靠审计清单）。
- 行为自洽：AI 每次按同一套规则做（靠 AGENTS + 必报，仍是"自觉执行"）。
- 要变成"强制执行"，需要执行器；V0.5 已交付 P6 编排 + 只读检查器（见 §4.1）。

### 4.1 自动门禁（V0.5）

- **只读检查器**：[`../使用说明/资产/工具_门禁检查器.py`](../使用说明/资产/工具_门禁检查器.py)，单文件、无依赖，对目标项目跑四项门禁（AGENTS 结构 / 证据与项数 / 交叉引用 / 任务状态与断点）。
- **阻断而非自愈**：不过项退出码 1 并指病层；不自动改文件，避免"为变绿而改绿"。
- **编排在提示词**：P6 负责四问、原样贴输出、病层分流与断点续跑；检查器是可复现的机检，不替代人工验收。
- **边界**：本仓自身仍不接入门禁与自动回写（手工维护声明不变）。

### 5. 三个门禁

人只在三处拍板：**需求确认、方案拍板、验证报告验收**。其余交给 AI 与执行层。

### 6. 身份边界与复制分发（输入如何到使用者手里）

| 区域 | 归属 | 维护者 | 使用者 |
|---|---|---|---|
| `使用说明/`（入口/操作说明/机制/FAQ/资产） | 工具资产 · **使用者只读区** | 全权维护 | 只读、复制到会话、复制模板到自己项目；**改动一律走送检反馈** |
| `维护/` + 根 `AGENTS.md` | 修改者侧 | 全权维护（AGENTS 自动加载 = 修改纪律硬约束） | 不需要读、不进 |
| **目标项目**（本仓外，使用者自选任意文件夹） | 使用者地盘 | 不介入（只收工具环候选） | 任意创建与修改，含项目 AGENTS 的项目环章节 |
| 目标项目内 `docs/模板/` | **输入副本** | 改源头 = 改本仓 `使用说明/资产/` | **只读**；项目内改副本 = 双源，禁止 |

**复制分发原则（对使用者的唯一口径）**：6 模板 + 质检清单 + 检查器在建项时**复制进目标项目 `docs/模板/`**——复制件是该项目唯一输入源，**只读、随项目冻结**；工具仓后续调整**只影响新项目**，**不设升级/同步动作**。提示词不复制（在 `操作说明.md`，用时复制到会话）。防的是"聊天粘贴版 vs 文件版"这类项目内双源与不可复读。

## 六、修改三步

1. **分层修复**：病在提示词/模板/质检/使用说明哪一层，只改那一层；跨层连改是事故之源。
2. **经确认执行**：动手前先读 `修改记录.md` 末 3 条与相关条目；向用户说明改哪、为什么、影响哪些引用，确认后动手。
3. **改一处 → 审计 → 归档**：
   - 跑 `审计清单.md` 的 grep；
   - 给使用者的指导写进 `使用说明/`（常见问题或机制）；
   - 过程与时间写进 `修改记录.md`；
   - 种子里不写实录。

## 七、已知边界

- **复制即冻结的代价**：目标项目输入不随工具仓升级，输入侧缺陷修复只进新项目——刻意取舍，不是缺陷；项目内副本被改动 = 双源，靠目标 AGENTS `docs/模板/` 只读条约束，审计时留意。
- **无固定回归夹具**：黄金样例与 `--selftest` 已按拍板移除，检查器不再有随仓基准；改检查器代码后必须对真实目标项目跑 `--root` 实测（验收见 §八），以"六条 grep + 实测"替代原回归。
- **只读且需人主动运行**：检查器不改文件、不接入会话钩子；它阻断的是"一次检查"，不是 AI 的每次动作——强制执行仍需人先跑 P6。
- **学习仍需人拍板**：候选可由 AI 生成，但"确认/否决"必须由人完成；工具环回灌也由人执行——这是刻意边界，不是缺陷。
- **多真源风险仍在**：提示词/模板/质检之间仍有重复表述，每次改动必须跑审计。
- **样例展示**：标准路径的产物形态已无随仓样例可对照，使用者按 `操作说明.md` 各步"产出 / 验收"自查；后续如需演示分支（如"不通过返工"），需另行拍板新增。

## 八、验收

- **角色验收**：使用者只读 `使用说明/` 能走完主线；修改者只读 `维护/项目介绍.md` + `修改记录.md` 能改对工具侧。
- **引用验收**：跑 `审计清单.md` 的六条 grep，零异常。
- **机制验收**：目标项目根开新会话，先输出续接四问，三问答对（V0.2 结构化状态 + 强制入口协议）。
- **学习验收**：跑 P5 产出学习记录，候选有证据、根因单层；确认后项目规则生效，并在下一任务/新会话被验证。
- **门禁验收**：`python 使用说明/资产/工具_门禁检查器.py --root <一个合规目标项目>` 返回退出码 0；对存在缺章节/缺证据的项目返回退出码 1，且每条问题病层指向正确（改检查器代码后必跑）。

## 九、维护经验（原 §六 8–14 迁移）

> 这些是"改工具侧"时的高频坑；使用者排障见 [`../使用说明/常见问题.md`](../使用说明/常见问题.md)。

| # | 现象 | 判断 | 处置 |
|---|---|---|---|
| 8 | 提示词只说"按模板"，AI 反问模板在哪或自编结构 | 模板引用是泛称，不是"文件名 + 输入槽" | 补输入槽并写明文件名 |
| 9 | 同一产物两处都在生成 | 同一输出有两个生成点 = 违反唯一责任人 | 收敛唯一 owner，另一处改引用 |
| 10 | 只修了某个项目的实例，没修模板/提示词 | 同一错误跨 run/跨项目复现 = 工具侧缺陷 | 修工具侧，再按需回填实例 |
| 11 | 质检判据把模板授权的内容判违规 | 判据限定词过宽 | 收紧限定词，回查此前是否误伤 |
| 12 | P0 把样例/模板当成真实需求消费 | 缺输入槽或输入卫生门 | 补输入槽 + 转正件核验门 |
| 13 | 同一产物在不同文档里叫法不一 | 称谓未统一 | 统一名称并同步全部引用 |
| 14 | "改名"被执行成复制，两份并存 | 未用 git mv / 旧名未清零 | `git mv` + 删旧文件 + 旧名 grep 零残留 |
