# 模板：技术选型方案 · 九节结构契约（P0 产出标准）

> 使用说明：`../README.md`（主线）与 `../流程与机制.md`（机制）
> 配套：同目录 `模板_AGENTS项目规范.md`、`模板_验证阶段工作流.md`
> **用法**：P0 提示词（`../prompts/P0_选型.md`）要求"按本模板九节生成"。每节标注**下游消费方**——这份结构是给 AI 的**管线契约**：缺一节，下游就无依据。
> 标注：**【必填】** = 缺了下游断链 ｜ **【有则填】** = 有素材才写
> 实例参考（外联真实产出）：emu-pilot 项目的技术选型方案（阶段 0–1 已回写结论）

---

## 文件头（元信息）【必填】

```markdown
- 日期：{YYYY-MM-DD}
- 依据：{需求文档路径，可选}
- 状态：**草案 → 待拍板 → 已拍板**（当前态加粗）
- 平台：{目标平台}；受控对象：{自动化对象}
```

> 下游：AGENTS §2.4 回写按"日期 + 文件名"定位；状态字段是 §6/§7 拍板与否的凭据。

## 1. 目标与能力表 【必填】

- 从需求文档提炼：`| 能力 | 说明 |` 表，3–6 项。

> 下游：P1 → AGENTS **§1.1** 项目定位与能力表。

## 2. 选型总体原则（含自研聚焦边界）【必填】

- 3 条左右本项目特有的原则（如：迭代速度优先 / 稳定性优先于性能 / 每层可替换）。
- **必须包含"复用优先、自研聚焦"**：明确列出自研的 **2–3 项**（例：流程引擎/配置模型/桌面 GUI），其余一律复用成熟开源。

> 下游：P1 → AGENTS **§5.1** 技术选型原则 + **§五** 复用优先声明。

## 3. 整体架构分层与模块划分 【必填】

- 分层图或分层列表（如：UI 层 / 编排层 / 识别层 / 设备层 / 基础设施层）。
- 模块清单表：`| 模块 | 职责一句话 |`。
- **模块命名按目标语言惯例**：Python 一律 snake_case（`import task_engine` 合法、`task-engine` 为语法错误）；发行名可用连字符。本表是 AGENTS 模块表唯一来源，命名错误会一路传染到包结构。

> 下游：P1 → AGENTS **§6.1 模块职责表**——这是它的**唯一来源**；本节缺失，P1 只能瞎编模块。

## 4. 按能力域候选对比 【必填】

- 每个能力域一张表：`| 候选 | 说明 | 结论 + 理由 |`，结论用三级标记：✅ 主选 / ⚠️ 备选 / ❌ 否决（+一句理由）。

> 下游：P1 → AGENTS **§1.3 技术栈状态行**。

## 5. 否决项汇总（防翻案） 【必填】

- `| 被否方案 | 一句理由 |` 集中一表（从各域 ❌ 汇总）。

> 下游：P1 → AGENTS **§1.3 否决清单**——AI 后续不得擅自翻案。

## 6. 最终推荐组合 / 变体对比与拍板记录 【必填】

- 2–3 个整体变体：构成一句话 / 综合利 / 综合弊 / 适用场景。
- 拍板结果表：`| 问题 | 决定 |`；未拍板则文件头状态 = **待拍板**。
- 最终推荐组合（一段或一张清单）。

> 下游：AGENTS 基线声明；依赖清单来源。

## 7. 分阶段技术验证路线 【必填 · 管线心脏】

- 按阶段小节（阶段 0、1、2…），每阶段一表：

```markdown
| 验证项 | 通过标准（量化） | 不通过的决策 |
|---|---|---|
| {编号} {验证项名} | {指标} {阈值}（{样本量/测量方法}） | {备选 A}；仍不达标 → {备选 B / 回到哪一决策} |
```

**标准三要素**：指标 + 阈值 + 样本量/测量方法（例：`单张截图 ≤500ms（预热1次后连测10次，取最大值）`）。
**阈值纪律**：必须给依据（业界常值/设备能力/业务需要），给不出的标 **【阈值待拍板】**；禁止"较快、足够、稳定"等不可测词。
**不通过的决策**：必须是可选备选（A/B），不得写"再优化"；每阶段定义**产出物**。

**标准四问**（每个验证项过一遍，任一答不出 = 回炉）：

1. **怎么测？**（步骤能照着执行吗）
2. **测几次、怎么判？**（样本量 + 统计口径：最大值/平均/成功率）
3. **阈值哪来的？**（依据，或明标【待拍板】）
4. **失败走哪条？**（备选是否真实存在于本表）

**合规/前置确认阶段**：若设此类阶段（如合规书面确认），必须写明**确认主体**（业务方/法务/使用者本人自担），避免无人可确认导致门禁死锁。

> 下游：P1 → AGENTS **§1.2 判定条件**；P2 → 分册**验证项清单**；P3 → 逐项执行与数据采集；P4 → 汇总证据表与总体结论；AGENTS **§2.4** 结论回写目标；**§1.6** 每阶段进度来源。
> **阶段收口（P4 回写）**：每阶段表下追加一行"验证结论：{通过 N / 不通过 M / 待补测 K / 不适用 J}（报告：`docs/技术选型/{日期}_选型验证报告.md`）"；本文件不承载证据表，阈值也不因报告而改。

## 8. 依赖清单、版本约束与合规边界 【必填】

- 依赖表：`| 层 | 包 | 版本约束 | 用途 |`；版本约束方式（锁文件为唯一事实源、`>=X,<Y` 分层纪律）。
- **开发与测试工具链**：测试/linter/格式化/依赖管理按语言生态列全（如 Python：pytest、pytest-cov、ruff、uv）——它们是 AGENTS §七 工具行与 dev 依赖声明的来源。
- 合规边界表：平台条款 / 行为边界 / 频率控制 / 数据隐私 / 许可证白名单 / 责任边界。

> 下游：P1 → AGENTS **§五 依赖管理** + **§1.4 合规边界**。

## 9. 未决项 / 待拍板 □ 清单 【有则填】

- 每条：`□ {问题} —— 需要什么信息才能定`。

> 下游：P1 → AGENTS **§1.6 挂起待拍板** 队列。
